
## 질의 임베딩 (Query Embedding)

- Retriever의 정의: 비정형 텍스트 질의를 입력 받아 관련 Document 객체 목록을 반환하는 표준 모듈
- `as_retriever()`: 기존 VectorStore 객체를 검색 전용 컴포넌트로 즉시 반환
- 문서 포멧팅: 검색된 Document 리스트의 page_content를 줄바꿈 문자로 병합
- LCEL 파이프라인 (LangChain Expression Language Pipeline)
	- Retriever -> Format -> Prompt -> LLM -> StrOutputParser 순으로 데이터 전달

## 벡터 검색 실행, 결과 분석

- 각 문서가 질문과 얼마나 의미상 일치하는지 유사도 점수(Score)를 통해 눈으로 직접 확인하는 과정
- `similarity_search_with_score()`: 검색 결과와 매핑된 유사도 수치 수집 및 신뢰도 평가
- 유사도 점수 해석과 거리 지표 원리
	- 0에 가까울수록 질문과 일치하는 거리(Distance) 지표인지, 1에 가까울수록 일치하는 유사도(Similarity) 지표인지 명확히 판별해야한다.
	- 코사인 유사도 (Cosine Similarity): 두 벡터의 방향이 완정히 일치하면 1, 직교이면 0, 정반대이면 -1
	- 코사인 거리 (Cosine Distance): 데이터베이스에서는 `거리` 개념을 위해 <mark>1 - 코사인 유사도</mark> 공식 사용
- 유사도 점수 구간별 판단 기준
	- 우수 구간 (0.0 ~ 0.35): 질문의 핵심 의도와 문서의 내용이 직접적으로 부한하는 상태
	- 보통 구간 (0.35 ~ 0.60): 주제는 관련되어 있으나 세부적인 조건이나 키워드가 일부 일치하는 상태
	- 주의 구간 (0.60 초과): 질문과 의미적 연관성이 거의 없으며 노이즈로 작용할 가능성이 높은 상태
- 검색 결과 디버깅 및 품질 분석
	- 원치 않는 엉뚱한 문서가 검색되었을 때, 문제의 원인을 단계별로 추적하고 바로잡는 체계적인 트러블 슈팅(Troubleshooting) 기법
	- 일부러 모호한 질문이나 완전히 다른 도메일의 질문(Out-of-Domain)을 던져보는 네더티브 테스트를 통해 점수의 변동 폭 관찰
	- 노이즈를 걸러낼 적정 임계값(Threshold) 기준을 찾는다.
	- 관련 질문 테스트
	- 무관한 질문 테스트
- 검색 실패 시 점검 체크리스트
	- 1순위 점수 과다(거리 점수 0.6 이상): 관련된 지식 문서 자체가 누락되었는지 확인
	- 엉뚱한 문서 상위 노출: 청크가 너무 길어서 여러 주제가 섞여 임베딩의 초점이 흐려졌는지 검토
	- 동음이의어 왜곡: 질문 문장의 특정 단어가 엉뚱한 문맥으로 임베딩 되었는지 질문 문장 구조 재점검

## Top-k
>질문과의 유사도 점수가 가장 높은 문서를 몇 개까지 가져올지 결정하는 핵심 파라메터

- 트레이드오프
	- 과도하게 큰 경우: 불필요한 정보(노이즈)가 포함되어 입력 토큰 비용 증가, 핵심 문맥이 흐려진다.
	- 과도하게 작은 경우: 필수적인 근거 문장이 누락되어 환각(Hallucination)이 발생할 위험
	- 적정값 설정 기준: 일반적으로 단답형 질의는 `k=2~3`, 종합 분석형 질의는 `k=4~6`범위에서 품질 테스트 진행

## Score Threshold
>검색된 문서가 통과해야 하는 최소 유사도 기준선(임계값)

- 코사인 거리 기준 설정 원리
	- 코사인 거리(1 - 유사도)를 기본 지표로 사용
	- 거리 점수가 큰 문서는 즉시 탈락(Filter-out) 처리
	- 우수 구간: 0.00 ~ 0.35
	- 보통 구간: 0.35 ~ 0.60
	- 주의/탈락: 0.60 초과
- 문맥 정제 (Context Pruning): 검증된 문서만 전달하여 환각과 비용을 줄이는 과정

## 메타데이터 필터링 검색
>문서의 속성 정보를 기준으로 검색 후보군을 사전에 압축하는 기술
>명확한 사실(Fact) 조건을 충족하는 문서만 정확히 골라내어 검색 품질을 크게 높인다.

- 메타데이터의 역할
	- 의미 유사도의 한계: 의미적 유사성을 기반으로 탐색하므로, 2023년 규정과 개정된 최신 규정처럼 문장 구조가 유사한 경우 구 버전을 오답으로 가져올 위험 존재
	- 사전 필터링(Pre-filtering): 벡터 거리 계산 전 메타데이터 조건을 먼저 평가하여 조건에 맞지 않는 문서를 즉시 제외
	- 연산 효율 향상: 조건을 만족하는 특정 그룹 내에서만 검색을 수행하므로 검색 속도와 정확도가 동시에 향상
- `PGVector`의 메타데이터 검색
	- JSONB 기반 속성 보관
	- 단일 조건 문법: `filter={"category": "장학"}`
	- 다중 조건 문법: `filter={"category": "장학", "year": 2024}`
		- 복합 필터 (Composite Filter)

## 프롬프트 설계

- 문맥 주입(Context Injection): AI에게 참고 문서를 지침과 함께 명확히 전달하여 자체 지식에 의한 왜곡을 차단하는 기술
- 문맥 주입의 목적과 환각 제어
	- 외부 지식 강제: 프롬프트에 직접 입력된 최신 문서를 최우선 기준으로 채택하도록 만든다.
	- 답변 범위 한정: "제시된 문서 내용 외에는 답변하지 말 것"이라는 제약 조건 부여, 허위 정보 생성 방지
- RAG 프롬프트 템플릿의 3요소
	- 시스템 역할 및 지침(System): 역할, 답변 어조, 참고 문서 외 임의 답변 금지 규칙 명시
	- 참고 문맥(Context): 검색을 통해 추출된 복수의 문서 본문 입력
	- 사용자 질문(Question): 사용자가 실제로 입력한 자연어 질문
- 컨텍스트 길이 관리와 최족화
	- <mark>Lost in the Middle</mark> 현상
		- 프롬프트 길이가 지나치게 길 경우, 언어 모델이 문서의 시작과 끝부분 정보를 잘 기억하지만 중간 부분에 위치한 핵심 정보를 누락하는 현상
	- 문맥 길이 제어 전략
		- Top-K 최적화
		- 불필요한 공백 및 메타데이터 정제 

## 검색 -> 생성 체인 통합

- LCEL(LangChain Expression Language) 데이터 파이프라인
- 단일 입력 분기와 병합 구조
	- 입력 분기: 사용자의 질문이 검색기와 질문 보존 경로로 동시 진입
	- 분맥 생성 경로: 검색기(Retriever)로 문서를 찾고, 포맷팅 함수로 묶어 전달
	- 질문 유지 경로: `RunnablePassthrough`를 통해 사용자 질문을 그대로 프롬프트에 전달
	- 파이프 연산자(`|`): 선행 작업의 결과값을 후행 작업의 입력값으로 넘겨주어 전체 과정을 하나의 체인으로 만든다.
		- 통합 체인(Integrated Chain)

## 출처 표기, 응답 후처리

- 문서 메타데이터 활용
	- 출처의 근거: 검색기(Retriever)가 찾아낸 문서의 원본 데이터를 버리지 않고, 체인 마지막 단계에서 답변과 함께 출력
- RAG 응답 후처리
	- 정보 추출 및 문자열 포맷팅
		- 응답 분리: 생성 답변과 출처 리스트를 나눈다.
		- 시각적 정렬: 출처 리스트를 순서대로 나열하여 텍스트 형태로 깔끔하게 조립
- 후처리 (Post-processing): 인공지능이 응답을 마친 후, 결과 데이터를 화면에 보기 좋게 리스트업하거나 정리하는 마무리 작업

## 키워드 검색과 BM25 알고리즘

- BM25 알고리즘
	- 문서 안에 특정 단어가 얼마나 자주 나오는지(단어 빈도, TF)
	- 전체 문서들 사이에서 그 단어가 얼마나 희귀한지(역문서 빈도, IDF)
	- 종합 계산해 순위를 매기는 대표적인 **키워드 검색 알고리즘**
	- 사용자가 입력한 고유명사나 전문 용어가 본문에 질제로 존재하는지 여부를 빠르고 정확하게 찾아내는데 탁월
- 키워드 검색의 원리와 3대 계산 요소
	- 단어 빈도(TF, Term Frequency): 한 문서 안에 자주 등장할수록 해당 문서의 관련도 점수가 올라간다.
	- 역문서 빈도(IDF, Inverse Document Frequency): 여러 문서에서 너무 흔하게 나오는 일반 단어는 가중치를 낮추고, 희귀한 핵심 단어에 높은 가중치 부여
	- 문서 길이 정규화: 문서의 길이가 비정상적으로 길때 단어의 점수가 과도하게 높아지지 않도록 문서 전체 길이에 비례해 보정
- 토크나이저(Tokenizer) 역할
	- 긴 텍스트 문장을 검색 시스템이 분석할 수 있도록 가장 작은 단위로 토큰(단어) 목록으로 쪼개는 도구
	- 분절 기준: 띄어쓰기 공백 기준으로 나누거나 한국어 형태소 단위로 분절하여 BM25 알고리즘에 단어 목록 전달
- 희소 검색(Sparse Retriever): 단어의 형태적 일치 여부와 빈도수만을 계산하여 문서를 찾는 방식

## Hybrid Search

- Hybrid Search 구조
	- 벡터 검색 기능과 단어 기반 BM25 알고리즘을 결합하여 상호 보완적인 검색망 완성
	- 단어는 다르지만 뜻이 통하는 문서(벡터)와 문맥 파악이 어려운 고유 규정명(BM25)를 동시에 확보
- EnsembleRetriever
	- 두 검색기가 각자 찾아온 상위 문서 목록에 가중치(Weights)를 곱해 단일 순위 점수를 계산
	- 동등한 비중(0.5:0.5)으로 출발하여 데이터 특성에 맞게 특정 검색기의 영향력 조절

## RRF, 가중치 튜닝

- RRF(Reciprocal Rank Fusion, 상호 순위 융합)
	- 여러 검색기를 '순위(등수)'를 기준으로 공정하고 규형있게 합쳐주는 알고리즘
	- 절대 점수 대신 '몇 등을 했는가'의 순위 역수를 매겨 공정한 단일 순위표로 통함
- RRF의 필요성
	- 점수 체께의 불일치
		- MB25 점수는 문장 길이나 단어 빈도에 따라 0부터 수십점까지 치솟지만, 벡터 유사도는 0과 1사이로 측정
		- RRF 해결책: 절대적인 점수를 배제하고 각 검색기에서의 '등수'를 역수로 변환($\frac{1}{\text{순위} + k}$)하여 합산
		- 상수 $k$의 역할: 일반적으로 $k = 60$을 적용하여 1위와 2위의 점수 차이가 과도하게 벌어지는 현상 방지
- 질의 유형에 따른 가중치 분배 전략
	- 키워드 중심 질의: 사규 명치, 에러 코드, 고유 시스템명 검색 시 BM25의 가중치 상향 (`weights=[0.8, 0.2]`)
		- 고유명사, 약어 중심
	- 의미 중심 질의: 구체적인 단어가 기억나지 않고 의도 중심이 ㄹ경우 벡터 검색의 가중치 상향 (`weights=[0.2, 0.8]`)
		- 의도, 서술형 위앙스
- 가중치 튜닝
	- 키워드 검색(BM25)과 벡터 검색 사이의 가중치(가령 가중치 계수 $a$)를 다양하게 조절해 보며, 문서들의 순위가 어떻게 역전되고 재배치되는지 관찰
